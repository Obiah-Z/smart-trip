# 后续迭代规划

本文基于当前 `smart-trip` 分支的实际完成度整理，目标不是重复描述已完成工作，而是给出下一阶段最值得投入的方向、优先级排序、执行顺序与验收标准。

当前系统已经完成了以下关键能力：

- 规划 / 咨询双链路
- Context 组装
- 长短期 Memory
- 会话追问与澄清恢复
- 真实本地 RAG
- Skill / Sandbox / 多 Agent
- 用户视图 / 开发调试视图拆分
- 基础测试与文档沉淀

因此，后续重点不应继续横向堆更多概念，而应转向：

1. 质量评测与稳定性
2. RAG 深化与真实知识源
3. 实时工具能力
4. 产品化能力完善
5. 观测、成本与部署

---

## 一、总体优先级

建议按以下优先级推进：

### P0

- 建立标准评测集与自动回归
- 收紧结果一致性校验
- 做 RAG 离线评测与污染分析
- 提升多轮追问稳定性

### P1

- 接入更真实的原始知识源
- 升级 hybrid retrieval 与 rerank
- 接真实天气 / POI / 路线服务
- 增加结果版本对比与正式方案保存

### P2

- 增加导出能力
- 增加统一观测、耗时与成本统计
- 增加部署方案与运行治理
- 视规模决定是否引入外部向量数据库

---

## 二、P0 阶段：质量与稳定性优先

这一阶段的目标是把当前系统从“功能能跑”推进到“结果稳定、缺陷可复现、效果可量化”。

### 2.1 建立标准评测集

建议建立一套固定测试集，覆盖至少以下场景：

- 简单天气问答
- 简单景点推荐
- 多日旅行规划
- 预算提升后的续问重算
- 酒店舒适度升级
- 目的地缺失后的澄清恢复
- 天数缺失后的澄清恢复
- 前一轮城市咨询、后一轮规划续接
- 多偏好冲突场景
- 否定偏好场景
- 雨天 / 亲子 / citywalk / culture 等主题场景

建议为每条样例记录：

- 输入
- 期望任务类型
- 期望目的地
- 期望天数
- 期望是否触发澄清
- 期望是否走多 Agent
- 期望主要技能
- 期望关键偏好是否命中

### 2.2 增加结果一致性校验

当前系统虽然已经比最初稳定，但仍建议增加统一规则校验层，重点检查：

- `summary.days` 是否与 `days[]` 长度一致
- 预算拆分是否与总预算关系可解释
- 规划任务是否真的生成了住宿建议
- 咨询任务是否错误进入完整规划链路
- 追问续算时是否错误丢失目的地 / 天数 / 节奏
- 规划摘要是否与结构化结果冲突

建议把这部分做成可复用的 validation 模块，而不是散落在各 Agent 或前端展示逻辑中。

### 2.3 做 RAG 离线评测

重点比较以下模式：

- BM25 only
- Vector only
- BM25 + Vector

建议统计的指标：

- Top1 命中率
- Top3 命中率
- MRR
- Cross-destination Pollution Rate
- Topic Coverage
- 平均召回耗时

目标不是把指标做得很复杂，而是能回答两个问题：

1. hybrid 是否真的比纯 BM25 更好
2. 哪类问题最容易出现跨城市污染或主题召回偏移

### 2.4 继续补会话稳定性回归

当前系统已经解决了很多追问问题，但仍建议把以下场景固化为回归测试：

- 先问深圳天气，再让系统规划三天行程
- 先生成杭州五日游，再只说“酒店住得更舒服一点”
- 先问景点推荐，再提高预算要求升级住宿
- 先缺失目的地，后补城市
- 先缺失天数，后补 `3天`

### P0 验收标准

- 关键回归测试全绿
- 有固定评测集和结果记录
- 能明确量化跨城市污染率与约束满足率
- 新增改动不会反复打破已修复问题

## 三、P1 阶段：RAG 深化与真实数据源

这一阶段的目标是把当前“本地真实 RAG”进一步升级成“更接近真实生产知识链路”的实现。

### 3.1 引入更真实的原始知识源

当前原始知识仍主要来自：

- `knowledge/cities.json`
- `mock/travel_data.json`

后续建议引入：

- 真实旅行攻略 Markdown
- 官方景区说明文档
- 城市文旅公开介绍
- 旅行注意事项、交通须知、季节性建议文档

建议统一放入：

- `backend/data/rag/raw_markdown/`
- 后续再通过脚本做 chunk 切分与索引构建

### 3.2 强化 chunk metadata

建议在现有 metadata 基础上，进一步增加：

- `source_name`
- `source_type`
- `updated_at`
- `reliability_score`
- `season`
- `suitable_for`
- `budget_level`

这样后续做 rerank、过滤和解释会更容易。

### 3.3 做更明确的检索前分类

当前 query rewrite 已经存在，但还可以继续增强：

- 先识别当前查询是偏攻略、偏住宿、偏路线、偏景点还是偏预算优化
- 不同类型使用不同的 query 构造策略
- 不同类型使用不同 topic 权重

### 3.4 增加 rerank 层

建议先从轻量规则 + 分数融合开始，再考虑更重的模型。

可引入的重排信号包括：

- 目的地严格一致
- 偏好匹配度
- 天数或节奏匹配度
- topic 命中度
- 来源可信度
- 时效性

### 3.5 增加知识版本管理

建议记录：

- 当前 corpus 版本
- 当前索引版本
- 语料更新时间
- 构建时间

方便回答“这次检索质量变化是因为代码改了还是知识改了”。

### P1 RAG 验收标准

- 已接入至少一批真实原始知识源
- 检索评测中 hybrid 模式优于 BM25 only
- 检索返回 metadata 更完整
- 可以清晰解释召回与重排的依据

## 四、P1 阶段：实时工具能力升级

这一阶段的目标是让系统逐步脱离“全部靠本地模拟结构化数据”的状态。

### 4.1 优先接真实天气服务

原因：

- 实现成本低
- 用户感知强
- 能立刻验证轻咨询链路价值

建议接入后：

- 增加缓存
- 增加失败降级
- 标注天气结果时效

### 4.2 接入真实 POI / 地点检索

建议支持：

- 景点位置查询
- 周边区域建议
- 路线可达性判断

### 4.3 接入路线距离 / 通行时间能力

这样规划链路可以不再只按“主题 + 区域”分组，而能进一步考虑：

- 地理邻近性
- 实际交通时间
- 节奏与当日负载

### 4.4 工具结果优先级治理

建议明确：

- 事实类信息优先走 Tool
- 背景知识优先走 RAG
- 最终输出必须说明哪些结论来自实时工具、哪些来自知识检索

### P1 工具层验收标准

- 至少接入 1 到 2 个真实外部服务
- 工具失败时主链路能自动降级
- 咨询链路与规划链路都能消费实时结果

---

## 五、P1 / P2 阶段：产品化能力完善

### 5.1 增加“正式方案保存”能力

当前系统更偏会话结果沉淀，后续建议增加更清晰的产品语义：

- 当前会话结果
- 用户确认保存后的正式方案

### 5.2 增加版本对比

适合的场景包括：

- 预算调整前后
- 住宿升级前后
- 节奏变化前后

用户需要一眼看到：

- 哪些内容变了
- 预算增加到哪里
- 为什么建议变了

### 5.3 增加“本轮调整摘要”

例如：

- 本轮提高了预算
- 本轮升级了住宿舒适度
- 本轮保持 5 天不变，只调整酒店

这样会明显提升追问体验。

### 5.4 增加导出能力

建议优先级：

1. Markdown
2. PDF
3. 后续再考虑图片或分享页

### 产品侧验收标准

- 用户可以保存正式方案
- 用户可以看到方案迭代差异
- 用户能明确理解这轮追问到底改了什么

---

## 六、P2 阶段：观测、成本与部署

### 6.1 增加统一 trace

建议一次请求统一打通：

- session_id
- request_id
- task_type
- retrieval_mode
- selected_skills
- agent path

### 6.2 记录耗时指标

建议记录：

- query rewrite 耗时
- retrieval 耗时
- embedding 耗时
- skill 执行耗时
- LLM 生成耗时
- full pipeline 总耗时

### 6.3 记录模型成本

至少拆分：

- 生成模型 token 消耗
- embedding token 消耗

### 6.4 增加部署方案

建议至少补：

- 本地生产启动方式
- Docker 方案
- `.env` 示例与依赖说明

### P2 验收标准

- 能追踪一次请求的完整链路
- 能看到各阶段耗时和成本
- 项目可以被更稳定地部署与复现

---

## 七、建议执行顺序

如果按三轮迭代推进，建议顺序如下：

### Sprint 1：质量收口

- 建评测集
- 补回归测试
- 做结果一致性校验
- 做 RAG 污染分析

### Sprint 2：RAG 深化与真实知识

- 接真实 Markdown 知识源
- 强化 metadata
- 做 rerank
- 优化 hybrid retrieval

### Sprint 3：真实工具与产品能力

- 接真实天气 / POI / 路线服务
- 增加版本对比
- 增加正式方案保存
- 增加导出与观测

---

## 八、当前最建议立刻做的三件事

### 1. 做标准评测集和指标

这是当前最缺的一层。没有评测，后续所有优化都难以证明价值。

### 2. 把原始知识源升级成真实攻略文档

这会决定 RAG 的真实上限，也能让系统更像一个真正有知识基础的旅行智能体。

### 3. 接一个真实实时工具

建议优先天气，其次 POI / 路线。这样可以最快让系统有一块能力真正脱离 mock。

---

## 九、结论

当前系统已经完成了从 Demo 向“可评估、可扩展、可展示原型”的关键跨越。

下一阶段不应再继续简单堆模块，而应把重心转向：

- 质量量化
- 检索深化
- 实时能力
- 产品闭环
- 工程可运维性

如果以上四块推进得当，这个项目后续不仅可以继续作为技术作品展示，也可以作为一套更完整的智能旅行规划系统原型长期演进。
