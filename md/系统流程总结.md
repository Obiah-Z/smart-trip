# 系统流程总结

本文基于当前 `smart-trip` 项目的实际代码实现整理，重点说明系统从用户输入到结果生成、再到会话与记忆沉淀的完整运行链路。这里描述的是当前仓库里已经落地的实现，不把未来规划和现状混在一起。

## 1. 系统整体结构

当前系统由三层组成：

1. 前端交互层  
   前端使用 Vue，主要负责收集用户输入、展示最终方案、展示追问入口、展示记忆与过程信息。接口调用入口在 `frontend/src/lib/api.js`，核心页面在 `frontend/src/App.vue`。

2. 后端编排层  
   后端使用 FastAPI，对外暴露 `/api/demo/plan`、`/api/memory/{user_id}`、`/api/skills` 等接口。应用启动和依赖装配在 `backend/app/main.py`，接口路由在 `backend/app/api/routes.py`。

3. 能力执行层  
   包含 Slot 抽取、任务分流、Memory、RAG、Skill 选择、Tool 执行、多 Agent 整合、LLM 总结、会话持久化等模块。旅行相关能力当前主要通过本地 Skill 脚本和 mock 数据驱动。

## 2. 一次请求是如何进入系统的

### 2.1 前端发起请求

用户在前端输入自然语言需求，例如：

`帮我规划一个杭州三日游，预算 3000，节奏轻松一点，酒店尽量安静，想吃本地特色`

前端通过 `createDemoPlan()` 调用后端：

- 接口：`POST /api/demo/plan`
- 请求体模型：`DemoPlanRequest`
- 字段包括：
  - `user_id`
  - `session_id`
  - `message`

如果是首次请求，前端通常没有 `session_id`；如果是追问或继续调整，则会沿用上一轮返回的 `session_id`。

### 2.2 FastAPI 接收请求

路由函数在 `backend/app/api/routes.py`：

- `/api/demo/plan` 收到请求后，会把 `user_id`、`session_id` 和 `message` 传给 `PlannerService.run()`
- 也就是说，系统的主执行入口实际上是 `backend/app/planning/planner_service.py`

## 3. 主链路总览

`PlannerService.run()` 是整个系统的编排中枢。当前主流程可以概括为：

1. 读取会话上下文
2. 抽取结构化槽位
3. 判断是否是补充澄清或基于旧方案继续调整
4. 生成当前轮 `structured_constraints`
5. 进行任务分流，判断是咨询类问题还是规划类问题
6. 如果关键信息不够，先返回澄清问题
7. 读取长期 Memory 和当前短期状态
8. 根据需要做 RAG 检索
9. 选择并执行相关 Skills
10. 如果是简单咨询，直接走轻量回答链路
11. 如果是规划任务，组装 Context，进入多 Agent 结果整合
12. 调用 LLM 生成更自然的摘要
13. 回写长期 Memory
14. 保存 session 运行结果，返回给前端

下面按模块展开。

## 4. Slot 抽取：系统先把自然语言变成结构化约束

这一层在 `backend/app/planning/slot_extractor.py`。

当前系统会从用户输入中提取这些关键字段：

- `destination`：目的地城市
- `days`：出行天数
- `budget`：预算
- `pace`：节奏，当前支持 `relaxed`、`balanced`、`intensive`
- `preferences`：偏好与约束标签

### 4.1 目的地提取

目的地优先从 `data/knowledge/cities.json` 动态读取城市列表，再回退到默认城市集合。  
这意味着系统不会固定写死只有杭州、北京、上海、成都，而是先看知识库里有哪些城市。

### 4.2 偏好提取

当前偏好抽取既支持正向偏好，也支持反向约束。例如：

- `想吃本地特色` -> `local_food`
- `不想吃本地特色` -> `avoid_local_food`
- `酒店尽量安静` -> `quiet_hotel`
- `酒店尽量嘈杂` 或 `热闹` -> `lively_hotel`
- `住得更舒服` -> `comfortable_hotel`

这一层已经做了正负偏好的冲突处理，避免同时把互斥标签写进去。

## 5. Session Context：系统如何续接上一次对话

这一层在 `backend/app/context/session_context_service.py`。

系统会根据 `session_id` 读取上一次运行结果，恢复这些信息：

- 历史消息 `history_messages`
- 上一轮结构化约束 `latest_structured_constraints`
- 上一轮任务类型 `latest_task_profile`
- 上一轮最终结果 `latest_final_plan`
- 上一轮新增记忆 `latest_memory_updates`
- 初始问题 `initial_request_text`
- 会话级基线约束 `session_baseline_constraints`

这样做的目的不是让模型自己去“回忆”，而是系统先把上一次任务的关键状态恢复出来，再决定本轮应该继承什么、覆盖什么。

## 6. Follow-up 与澄清恢复：系统如何理解“继续调整”

这部分逻辑也在 `PlannerService` 里，是当前系统比较关键的一层。

### 6.1 继续调整旧方案

如果上一轮是 `travel_planning`，并且这轮输入出现：

- `提升`
- `提高`
- `增加`
- `调整`
- `升级`
- `更舒服`
- `舒适度`

这类信号，系统会把它识别为在上一轮方案基础上的增量修改，而不是一次新的独立问题。

例如：

`帮我把预算提升到 10000，主要是提升住宿舒适度`

系统会尽量沿用上一轮的：

- 目的地
- 天数
- 原始偏好

再只更新这轮新增的预算和住宿偏好。

### 6.2 澄清恢复

如果用户第一次只说：

`帮我规划三天行程`

系统会发现缺少 `destination`，先返回补充问题。  
用户下一句只回复：

`深圳`

系统会把这句视为对上一轮缺失字段的补充，而不是一条新的独立需求。  
同理，如果用户说：

`帮我规划杭州行程`

系统会先问天数，后续用户只回复 `3天`，系统也会恢复原始问题并继续完成规划。

### 6.3 不再默认兜底杭州

当前实现已经去掉“缺城市就默认杭州”的兜底行为。  
如果规划任务缺少目的地，会先澄清，不会静默写成杭州。

## 7. Task Router：先分清是问答还是规划

任务分流逻辑在 `backend/app/planning/task_router.py`。

系统会先判断当前请求属于：

1. `travel_consulting`：旅行咨询 / 简单问答
2. `travel_planning`：多日规划 / 路线安排

### 7.1 咨询类问题

例如：

- `杭州天气怎么样`
- `杭州有哪些推荐景点`

这类问题通常走轻量链路，不应该强行进入完整路线规划。

### 7.2 规划类问题

例如：

- `帮我规划一个杭州三日游`
- `给我安排一个上海 4 天行程`

这类问题会进入完整规划链路，通常需要：

- RAG
- Tool / Skill 调用
- 路线生成
- 多 Agent 整合

## 8. 缺失字段检查：什么时候先问用户

在当前实现里，系统对缺失字段有一层明确策略：

- 如果缺少 `destination`，先问目的地
- 如果是 `travel_planning` 且缺少 `days`，先问天数
- `budget` 不是强制字段，没有预算也可以先生成基础方案

因此系统不会因为没写预算就卡住，但会因为缺失目的地或天数而进入澄清模式。

## 9. Memory 设计：短期状态和长期偏好怎么分

### 9.1 短期状态

短期状态就是当前轮或当前会话的结构化约束，本质上就是：

- 目的地
- 天数
- 预算
- 节奏
- 偏好标签

它直接来自 `structured_constraints`，是当前任务现场。

### 9.2 长期 Memory

长期记忆由 `MemoryService` 管理，底层存储在：

- 优先 SQLite：`backend/app/db/sqlite.py` 中定义的 `smart_trip.sqlite3`
- 如果 SQLite 不可用，则回退 JSON 文件存储

当前长期记忆主要保存用户稳定偏好，例如：

- `hotel_style`
- `preference_quiet_hotel`
- `preference_local_food`
- `preference_food`
- `travel_pace`
- 文化 / 自然 / 亲子 / 交通偏好

### 9.3 Memory 回写策略

在规划任务完成后，`MemoryService.persist_preferences()` 会把本轮确认的偏好写回长期记忆。

例如：

- `quiet_hotel` -> `hotel_style=prefer_quiet_location`
- `lively_hotel` -> `hotel_style=prefer_lively_location`
- `local_food` -> `preference_local_food=local_food`
- `avoid_local_food` -> `preference_local_food=avoid_local_food`
- 节奏会写成 `travel_pace`

这保证后续会话可以沿用稳定偏好。

## 10. Memory 注入：不是把所有历史一股脑塞给模型

这一层在 `backend/app/memory/memory_injection_service.py`。

系统不会把所有长期记忆原样拼进去，而是会根据当前问题筛选“和这次决策最相关”的那一部分。

筛选依据主要有两类：

1. 结构化偏好命中  
   例如当前问题明确提到了酒店环境偏好，就优先注入：
   - `hotel_style`
   - `preference_quiet_hotel`

2. 文本关键词命中  
   例如用户这轮提到“安静”“美食”“文化”“节奏”，系统会挑出相关记忆键

如果没有明确命中规则，但系统里已有长期记忆，也会回退注入最近几条，避免上下文完全失忆。

## 11. RAG：知识检索、重排、注入是怎么做的

这一层在 `backend/app/retrieval/retrieval_service.py`。

### 11.1 知识来源

当前项目的知识源来自本地 `data/knowledge/cities.json`，属于本地知识库驱动的 RAG demo。

### 11.2 检索条件

系统会基于这些字段拼接检索条件：

- `destination`
- `days`
- `budget`
- `preferences`

同时，还会把偏好扩展成查询词，例如：

- `family` -> `亲子`、`带娃`、`室内`
- `culture` -> `文化`、`历史`、`人文`
- `local_food` -> `本地特色`、`特色美食`
- `comfortable_hotel` -> `舒适`、`酒店`

### 11.3 检索与重排

当前实现会：

1. 先按城市筛出候选知识块
2. 计算 query term 和文档关键词的重合度 `lexical_overlap`
3. 计算偏好匹配分 `preference_bonus`
4. 对路线主题 `trip_route` 给额外加分
5. 做主题多样性选择，避免 Top-K 全部是同一种内容

### 11.4 注入结果

最终注入到 Context 的不是全部原文，而是重排后的少量 `injected_knowledge` 摘要。  
当前是一个轻量本地 RAG，实现思路是对的，但还不是向量库级别的生产方案。

## 12. Skills：系统有哪些能力，怎么被触发

### 12.1 Skill 的组织方式

当前系统的 Skill 都放在 `skills/public/` 下，每个能力一个目录，目录里至少包含：

- `SKILL.md`
- `scripts/run.py`

当前主要已接入的业务 Skill 有：

1. `weather.lookup`
2. `attraction.search`
3. `hotel.search`
4. `route.plan`
5. `knowledge.snapshot`

此外还有专门用于验证隔离机制的 sandbox 测试 Skill。

### 12.2 Skill 如何加载

`backend/app/skills/skill_registry.py` 会扫描 `skills/public/*/SKILL.md`：

- 读取 frontmatter 元数据
- 解析 `skill_id`
- 解析描述、触发词、输入 schema、依赖关系、优先级、sandbox policy
- 绑定到对应的 `scripts/run.py`

这样做的好处是 Skill 可插拔，新增能力时不需要改一堆硬编码注册表。

### 12.3 Skill 如何选择

Skill 选择逻辑在 `backend/app/skills/skill_selection_service.py`。

当前系统支持三层策略：

1. 咨询类快速路径  
   对简单天气 / 景点类问答，优先用轻量启发式选择，减少不必要的长链路。

2. LLM 选择  
   如果启用了真实模型能力，系统可让外部模型辅助判断该选哪些 Skill。

3. 启发式回退  
   如果 LLM 不可用，或返回异常，则用本地规则选择。

### 12.4 当前触发原则

大致可以概括为：

- 问天气 -> `weather.lookup`
- 问景点 / 美食 / 推荐 -> `attraction.search`
- 问住宿 / 安静 / 舒适 / 酒店 -> `hotel.search`
- 问按天行程 / 路线 / 规划 -> `route.plan`
- 问系统能力 / MCP / 知识桥接 -> `knowledge.snapshot`

### 12.5 依赖展开

`route.plan` 依赖 `attraction.search`。  
所以即使只选中了 `route.plan`，系统也会自动补上依赖 Skill。

### 12.6 多日规划自动补酒店能力

当前实现还有一层业务策略：

如果是多日旅行规划、天数大于等于 2、且目的地已确认，即便用户没显式说“酒店”，系统也会自动补充 `hotel.search`，避免最终方案没有住宿推荐。

## 13. Tool 执行：Skill 是怎么真正跑起来的

这一层在 `backend/app/skills/tool_service.py`。

执行流程是：

1. 根据 `skill_id` 从注册表取出 SkillDefinition
2. 根据输入 schema 自动构造 payload
3. 调用 `SkillScriptRunner`
4. 返回结构化结果：
   - `tool_name`
   - `display_name`
   - `provider`
   - `input`
   - `output`
   - `sandbox`

其中 payload 构造也做了业务补齐，例如：

- `days` 缺失时默认填 3
- `route.plan` 会自动从 `attraction.search` 的结果中提取景点名单

## 14. Sandbox：为什么需要，以及当前是怎么实现的

这一层在 `backend/app/skills/skill_sandbox.py`。

### 14.1 为什么需要 Sandbox

Skill 最终是脚本执行。  
一旦未来接入更复杂的外部工具、第三方脚本或更动态的执行逻辑，如果没有隔离层，就可能出现：

- 无限制占用 CPU / 内存
- 任意访问文件
- 任意联网
- 任意拉起子进程

所以当前项目给 Skill 执行加了一层受限子进程 Sandbox。

### 14.2 当前 Sandbox 的实现方式

每个 Skill 会在独立 Python 子进程中执行，并启用以下约束：

- 超时限制
- CPU 时间限制
- 内存限制
- 文件句柄数限制
- 可写目录限制
- 可选禁网
- 可选禁用子进程

Skill 的这些限制来自各自 `SKILL.md` frontmatter 里的 `sandbox_policy`。

### 14.3 当前实际效果

当前旅行 Skill 基本都运行在：

- 禁网
- 禁子进程
- 受控可写目录

的模式下。  
这说明当前项目的 Skill 能力虽然主要是本地 mock / 本地规则驱动，但执行治理边界已经搭起来了。

## 15. 多 Agent：当前项目是怎么协作的

这一层在 `backend/app/agents/agent_service.py`。

当前多 Agent 不是多个独立大模型互相对话，而是后端用多角色分工的方式，把整条链路拆成四个职责阶段：

1. `planner_agent`
2. `retriever_agent`
3. `executor_agent`
4. `reviewer_agent`

### 15.1 planner_agent

负责从约束和记忆中整理本次任务：

- 识别目的地、天数、预算
- 列出任务拆解
- 标记共享状态投影

### 15.2 retriever_agent

负责整理外部证据：

- 记录召回了多少知识
- 记录调用了哪些工具
- 输出 rerank trace

### 15.3 executor_agent

负责产出真正给用户消费的结构化结果：

- `summary`
- `budget`
- `days`
- `weather`
- `hotelRecommendation`
- `foodRecommendations`

也就是说，当前真正的 `final_plan`，实际上来自 `executor_agent.payload`。

### 15.4 reviewer_agent

负责最后做简单一致性校验，例如：

- 是否大致满足预算
- 节奏是否合理
- 是否有天气信息

最终给出：

- `approved`
- 或 `needs_review`

### 15.5 上下文共享方式

当前多 Agent 的共享不是自由对话，而是“统一状态 + 不同角色读取不同投影”。  
也就是所有 Agent 都围绕同一个运行时状态工作，但各自只消费自己关心的那一部分。

## 16. Context 组装：最终给模型看的上下文是怎么重建的

这一层在 `backend/app/context/context_assembler.py`。

系统会把当前轮信息整理成多段 Prompt Section，当前包含：

1. `System Role`
2. `Current User Request`
3. `Task Analysis`
4. `Structured Constraints`
5. `Session Context`
6. `Relevant Memory`
7. `Memory Injection Strategy`
8. `Retrieved Knowledge`
9. `Selected Skills`
10. `Tool Evidence`
11. `Output Contract`

### 16.1 为什么这样设计

这样做的核心目标是减少模型在长对话里“自己猜”。  
系统先把真正影响结果的硬约束放到前面，例如：

- 目的地
- 天数
- 预算
- 节奏
- 用户偏好

再把记忆、知识、工具证据按层次补上。  
模型不是从零开始想，而是在“已经整理好的工作现场”里继续生成。

### 16.2 如何提升准确性

当前设计里准确性主要靠以下几层保障：

1. 先结构化，再生成  
   先抽槽位、定约束，而不是直接让模型自由发挥。

2. 优先用外部证据  
   天气、景点、住宿、路线等信息优先来自 Skill 和检索，而不是纯模型脑补。

3. 长短期信息分层  
   当前问题、会话状态、长期偏好分别管理，避免互相污染。

4. 澄清先行  
   缺目的地或天数时先问，不强行生成。

5. Reviewer 校验  
   最终结果会有预算和节奏的兜底检查。

## 17. 咨询类问题的轻量链路

当前系统并不是所有问题都走完整路线规划。

如果 `TaskRouter` 判断是 `travel_consulting`，系统会走 `_build_consulting_response()`：

- 只做必要的 RAG / Skill 调用
- 不进入完整 Agent 规划流程
- 直接生成一个轻量 `final_plan`

例如：

### 17.1 问天气

如果工具结果是 `weather.lookup`，会返回：

- `consultingType = weather`
- 天气摘要
- 出行建议

### 17.2 问推荐景点

如果工具结果是 `attraction.search`，会返回：

- `consultingType = attraction`
- 景点推荐摘要

这样可以避免“只是问天气，却跑完整行程规划链路”的问题。

## 18. 规划类问题的完整链路

当请求被识别为 `travel_planning` 后，系统会进入完整规划链路：

1. 读取 Session
2. 抽取并合并约束
3. 读取并筛选 Memory
4. 做 RAG 检索
5. 选择 Skill
6. 顺序执行 Tool
7. 组装 Context
8. 跑多 Agent
9. 从 `executor_agent` 取 `final_plan`
10. 调用外部模型生成自然语言摘要
11. 回写 Memory
12. 保存本轮会话结果

## 19. LLM 在当前系统里承担什么角色

这一层在 `backend/app/llm/openai_client.py`。

当前 LLM 的职责主要有两个：

1. 技能选择辅助
2. 最终摘要润色

### 19.1 最终方案不是 LLM 从零生成的

当前系统里，LLM 不是直接生成整份结构化行程。  
真正的结构化结果先由：

- 规则抽取
- RAG
- Skills
- AgentService

组合出来。  
LLM 主要负责把 `final_plan` 转成更自然、更适合用户阅读的文字摘要。

### 19.2 降级策略

如果没有配置可用模型，或模型接口失败，系统会降级为：

- `mode=mock` 或 `mode=fallback`
- 继续返回本地规则生成的结果

这保证了系统在模型不可用时仍然能跑通主流程。

## 20. 数据如何持久化

底层仓储在 `backend/app/db/repositories.py`。

### 20.1 用户长期记忆

保存位置：

- SQLite 表 `user_memory`
- 或 JSON 文件 `memory_store.json`

### 20.2 会话运行记录

保存位置：

- SQLite 表 `session_runs`
- 或 JSON 文件 `session_runs_store.json`

每次 `/api/demo/plan` 返回前，系统都会把完整 response 保存下来。  
这样下一轮只要带上同一个 `session_id`，就可以恢复上一次的上下文。

## 21. 前端是如何展示这个流程的

前端当前采用“结果优先”的方式：

1. 顶部展示当前旅程状态和会话状态
2. 首屏优先展示最终结果 `ResultPanel`
3. 下方展示 Memory 面板
4. 继续追问输入框固定在结果后，方便用户直接改预算、节奏、住宿等条件
5. 过程信息放进折叠区 `Behind The Scenes`

这意味着用户优先看到的是“结果”和“继续调整入口”，而不是开发过程细节。

## 22. 当前项目最核心的闭环

如果只用一句话总结当前系统的核心闭环，就是：

**用户输入自然语言需求后，系统先把需求结构化，再结合会话状态、长期偏好、知识检索和技能执行结果完成咨询或规划，最后把结果回写到会话与记忆中，为后续追问提供连续上下文。**

换成更细一点的链路，就是：

`输入 -> 槽位抽取 -> 会话续接 -> 任务分流 -> 澄清/检索/工具 -> 多 Agent 整合 -> 结果生成 -> LLM 摘要 -> Memory/Session 回写`

## 23. 当前实现的定位

最后需要明确一点：当前仓库已经具备完整的“智能旅行规划系统”主链路雏形，但仍然是偏 demo / mock 驱动的实现。

具体表现为：

- RAG 基于本地 JSON 知识库
- Travel data 和工具结果大量来自本地 mock 数据
- 多 Agent 是规则化多角色协作，不是完全自治式 Agent 集群
- LLM 主要负责摘要和辅助选择，而非端到端独立决策

但从工程结构上看，这套系统已经把生产级系统最关键的骨架搭出来了：

- 有明确任务分流
- 有 Context 重建
- 有长期 / 短期 Memory
- 有 RAG 注入
- 有 Skill 注册与选择
- 有 Tool 执行隔离
- 有多 Agent 职责拆分
- 有 session 持久化与追问恢复

这也是它最适合在简历或项目介绍中表达的价值所在。
