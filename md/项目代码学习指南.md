# 项目代码学习指南

本文的目标不是重复介绍功能，而是帮你建立一条适合学习这份项目代码的阅读路径。这个仓库已经不再是一个纯 demo，它现在包含了旅行问答、行程规划、会话续接、Memory、RAG、Skills、Sandbox、多 Agent、地图展示、图片生成、前端双视图等多条链路。如果一上来按目录硬读，很容易迷失。

更有效的方式是：

1. 先建立整体心智模型
2. 再按一次真实请求的执行路径去读
3. 最后再下钻到某个模块做专题学习

## 1. 先用一句话理解项目

这份项目本质上是一个 `旅行智能体编排系统`：

- 前端负责采集用户自然语言需求，并以用户视图 / 开发调试视图展示结果
- 后端负责把一次输入拆成结构化约束、会话上下文、Memory、检索、Skills、Agent 结果，再统一合成为最终方案
- 数据层负责保存长期偏好、会话运行记录、本地 RAG 索引、mock 旅行数据、地图点位和图片缓存

你可以把它理解成：

`用户输入 -> 任务识别 -> 结构化约束 -> 会话恢复 -> Memory 注入 -> RAG 检索 -> Skill 选择与执行 -> Agent 整合 -> 最终方案 -> 前端展示 -> 会话/Memory 回写`

## 4. 这份项目最适合怎么学

最推荐的方法不是“看完一个目录再看下一个目录”，而是按下面三层来学。

### 4.1 第一层：先学主链路

先回答这个问题：

`一次 /api/demo/plan 请求到底经过了哪些模块？`

你应该先读下面这些文件：

- `backend/app/main.py`
- `backend/app/api/routes.py`
- `backend/app/planning/planner_service.py`

#### 你需要看懂什么

在 `backend/app/main.py` 里，你要看的是应用如何装配依赖：

- `SkillRegistry`
- `SkillScriptRunner`
- `ToolService`
- `OpenAIPlannerClient`
- `MemoryService`
- `RetrievalService`
- `PlannerService`
- `GeoPresentationService`
- `ImageGenerationService`

也就是说，这个项目不是在某个大框架里“自动发现”能力，而是在 `create_app()` 里显式把所有模块装起来。

在 `backend/app/api/routes.py` 里，你要看的是：

- 哪些 HTTP 接口存在
- 主入口是不是 `/api/demo/plan`
- 返回结构是什么
- 哪些接口是能力性的补充接口，比如图片生成、Memory、Skills、Session 历史

在 `backend/app/planning/planner_service.py` 里，你要看的是：

- `run()` 是不是整个编排中枢
- 它先做什么，后做什么
- 哪些分支会提前 return

#### 学到这里，你应该能回答

1. 前端发一个请求后，后端是从哪里接住的？
2. 为什么 `PlannerService` 是主编排层，而不是 `AgentService`？
3. 什么情况下系统不会进入多 Agent 规划链路？

### 4.2 第二层：再学“系统怎么理解用户”

这层的核心问题是：

`系统如何把一句自然语言变成当前轮可执行的结构化约束？`

重点看：

- `backend/app/planning/slot_extractor.py`
- `backend/app/planning/task_router.py`
- `backend/app/context/session_context_service.py`
- `backend/app/planning/planner_service.py` 里的这些方法：
  - `_resolve_structured_constraints`
  - `_resolve_effective_message`
  - `_resolve_task_profile`
  - `_is_followup_update`
  - `_is_clarification_recovery`
  - `_resolve_missing_fields`

#### 这一层建议这样读

先看 `SlotExtractor`，确认系统当前能抽哪些槽位：

- `destination`
- `days`
- `budget`
- `pace`
- `preferences`

再看 `TaskRouter`，理解系统如何把问题分成两类：

- `travel_consulting`
- `travel_planning`

这一步很关键，因为这个项目已经修过一个典型问题：

`用户只是问杭州天气或杭州有哪些景点时，不应该强行走完整路线规划`

然后再回到 `PlannerService` 看：

- 怎么识别“继续调整旧方案”
- 怎么识别“澄清后的补充回答”
- 怎么继承上一轮目的地 / 天数 / 偏好

#### 学到这里，你应该能回答

1. 为什么“杭州今天天气如何”不会走 `route.plan`？
2. 为什么“帮我把预算提升到 10000，主要提升住宿舒适度”会沿用上一轮方案？
3. 为什么“帮我规划三天行程”现在不会默认兜底杭州？

### 4.3 第三层：最后学“系统怎么执行能力”

这层包括：

- Memory
- RAG
- Skills
- Sandbox
- Agents
- 地图与图片展示

这部分不要一开始就全部一起看，建议按下面顺序分块学。

## 5. Memory 模块怎么学

相关文件：

- `backend/app/memory/memory_service.py`
- `backend/app/memory/memory_injection_service.py`
- `backend/app/db/repositories.py`
- `frontend/src/components/MemoryPanel.vue`

### 先理解职责分工

`MemoryService` 负责：

- 读取长期 Memory
- 写回长期偏好

`MemoryInjectionService` 负责：

- 从长期 Memory 里挑当前问题真正相关的那部分
- 给出“为什么用了这些记忆”的原因

`SessionContextService` 负责的是会话上下文，不等于长期 Memory。  
这两者一定要分开理解：

- `session_context` 解决“这一轮之前发生了什么”
- `memory_context` 解决“这个用户长期偏好是什么”

### 你要重点看什么

在 `memory_service.py` 里重点看 `persist_preferences()`：

- 偏好是如何写成结构化键值的
- `quiet_hotel` / `lively_hotel` / `local_food` / `avoid_local_food` 如何落库

在 `memory_injection_service.py` 里重点看：

- 哪些 key 和哪些用户表达是相关的
- 为什么当前问题会选中某条长期记忆
- 如果没有显式命中，为什么会回退注入最近几条记忆

### 你学完这一层应该能回答

1. 长期 Memory 和短期状态的边界是什么？
2. 为什么系统不会把整段原始对话直接存成 Memory？
3. 当前页面里“这次沿用了哪些偏好”是从哪来的？

## 6. RAG 模块怎么学

相关文件：

- `backend/app/retrieval/retrieval_service.py`
- `backend/app/retrieval/query_rewrite.py`
- `backend/app/rag/retriever.py`
- `backend/app/rag/corpus_builder.py`
- `backend/app/rag/vector_index.py`
- `backend/app/scripts.py`
- `md/RAG升级说明.md`

### 建议的阅读顺序

1. `retrieval_service.py`
2. `query_rewrite.py`
3. `rag/retriever.py`
4. `scripts.py`
5. `md/RAG升级说明.md`

### 先抓主结论

当前项目的 RAG 不是“直接读一个 JSON 模拟一下”，而是：

- 先准备 `raw markdown`
- 构建 `manifest`
- 生成 `BM25 index`
- 如果 embedding 可用，再叠加向量索引
- 检索时走 `hybrid retrieve`

### 重点理解两个问题

#### 1. 为什么要先做 query rewrite

用户原话往往不适合直接检索。  
系统会根据：

- `destination`
- `preferences`
- `days`
- `pace`
- `user_input`

生成更稳定的检索 query。

#### 2. 为什么 RetrievalService 不是直接调用大模型

这里的职责是：

- 先把知识检索做完
- 把排序结果和注入内容整理好
- 再交给后面的规划链路或 LLM 摘要使用

它本身是“证据准备层”，不是“答案生成层”。

### 启动时发生了什么

`backend/app/scripts.py` 里的 `ensure_rag_ready()` 会在必要时自动确保：

- markdown 语料存在
- index 存在
- embedding index 如果可用则尝试构建

这意味着这个项目不是要求你手工先跑一堆预处理脚本才能启动，而是在运行时做必要保障。

### 你学完这一层应该能回答

1. 当前 RAG 是 BM25、向量还是 hybrid？
2. `retrieval_context.injected_knowledge` 是怎么来的？
3. 为什么开发调试面板里能看到 `bm25_score / vector_score / hybrid_score`？

## 7. Skills、Tool 和 Sandbox 怎么学

相关文件：

- `backend/app/skills/skill_registry.py`
- `backend/app/skills/skill_selection_service.py`
- `backend/app/skills/tool_service.py`
- `backend/app/skills/skill_script_runner.py`
- `backend/app/skills/skill_sandbox.py`
- `skills/public/*/SKILL.md`
- `skills/public/*/scripts/run.py`

### 正确的理解方式

这个项目里的 Skill 不是“只是一个 Python 函数”，而是三层结构：

1. `skills/public/<skill>/SKILL.md`
2. `skills/public/<skill>/scripts/run.py`
3. 后端 `SkillRegistry / ToolService / SkillSelectionService`

也就是说：

- `SKILL.md` 定义能力元数据
- `run.py` 负责能力执行
- 后端编排层负责注册、选择、构造 payload、运行和回填结果

### 推荐阅读顺序

1. 先看一个最简单的 Skill 目录  
   例如 `skills/public/weather-lookup/`
2. 再看 `SkillRegistry`  
   理解它如何扫描 `skills/public/*/SKILL.md`
3. 再看 `SkillSelectionService`  
   理解系统何时选哪个 Skill
4. 再看 `ToolService`  
   理解 payload 如何从结构化约束组装出来
5. 最后看 `SkillSandboxRunner`

### 这一层最值得理解的点

#### 1. Skill 选择不是固定写死的

当前系统会根据：

- 当前问题
- 当前结构化约束
- follow-up 标记
- 是否是简单咨询

决定选哪些 Skill。

比如：

- 天气问题通常只选 `weather.lookup`
- 景点咨询通常只选 `attraction.search`
- 多日行程规划通常会补 `route.plan`
- 多日规划即使用户没显式提酒店，也可能按策略补 `hotel.search`

#### 2. Skill 不是直接在主进程裸跑

`skill_sandbox.py` 做了受限执行，包括：

- 独立子进程
- 超时
- 内存限制
- CPU 限制
- 文件打开数限制
- 禁网
- 禁子进程
- 受控写目录

这部分是你理解项目“工程性”很重要的一层。

### 你学完这一层应该能回答

1. Skill 是怎么从磁盘被发现并注册的？
2. 为什么简单天气问答只会调一个 Skill？
3. Sandbox 具体限制了什么？

## 8. 多 Agent 怎么学

相关文件：

- `backend/app/agents/agent_service.py`
- `frontend/src/components/PipelinePanel.vue`

### 先理解一个事实

当前多 Agent 不是一套分布式 agent framework，也不是多个模型并发互聊。  
它是一个 `按角色拆职责的串行编排层`。

当前角色包括：

- `planner_agent`
- `retriever_agent`
- `executor_agent`
- `reviewer_agent`

### 每个角色干什么

`planner_agent`

- 负责任务拆解
- 汇总约束和关键记忆

`retriever_agent`

- 汇总检索结果和工具证据

`executor_agent`

- 负责把路线、酒店、天气、景点结果整合成最终 `final_plan`
- 这里也是用户视图数据最主要的来源

`reviewer_agent`

- 做预算、节奏、天气可用性等基础校验

### 学习时要特别注意

前端用户看到的大部分结果，不是 LLM 自由写出来的，而是 `executor_agent` 把工具与检索结果结构化整合出来的。

这也是为什么当前项目能比较稳定地展示：

- `dailyGuide`
- `hotelOptions`
- `attractionRecommendations`
- `foodRecommendations`
- `budgetInsights`
- `tripTips`

### 你学完这一层应该能回答

1. 当前的多 Agent 是并行还是串行？
2. 用户最后看到的旅行方案，主要是谁组装出来的？
3. `reviewer_agent` 在哪里做预算和节奏检查？

## 9. 地图和图片展示怎么学

这部分是项目后期增强层，不建议一开始就深挖，但可以在主链路看懂后再补。

相关文件：

- `backend/app/presentation/geo_service.py`
- `backend/app/integrations/amap_geo_service.py`
- `frontend/src/components/TripMapPanel.vue`
- `frontend/src/components/AmapTripMapPanel.vue`
- `backend/app/image_generation/service.py`
- `md/景点图片生成模块说明.md`

### 地图层的职责

`GeoPresentationService` 负责把已有规划结果再增强为前端可展示的地图结构：

- `center`
- `markers`
- `routes`
- `bounds`
- `diagnostics`

这里很重要的一点是：

地图层不是重新规划路线，而是把已经生成好的 `final_plan` 转成“适合前端地图展示的结构化可视化数据”。

### 图片层的职责

`ImageGenerationService` 是单独的图片生成能力：

- 有缓存
- 有本地落盘
- 通过 `/api/images/attraction/generate` 对外提供能力

这部分不属于最核心的规划主链路，但属于项目产品化增强的一部分。
